# 实时语音通话方案设计 (基于 WebSocket)

本文档旨在描述如何基于现有的 WebSocket 基础架构，将灵枢 AI 的 ASR、LLM 和 TTS 模块整合为低延迟的实时语音通话系统。

## 1. 现状分析

目前语音交互主要依赖传统的 REST API 模式：
- **请求-响应模式**：前端录音结束后上传整个音频文件 -> ASR 识别全句 -> LLM 生成回复 -> TTS 合成全句音频 -> 前端下载并播放。
- **高延迟**：用户必须在说话结束后等待数秒才能听到回应，无法实现流畅的通话体验。
- **非全双工**：AI 说话时无法实时监听用户输入，不具备打断（Barge-in）能力。
- **资源浪费**：如果用户在中途打断，后端仍在继续合成和传输已失效的音频内容。

## 2. 优化方向

- **全双工流式交互**：采用 WebSocket 实现音频流的双向实时传输。
- **极低首包延迟 (TTFB)**：
    - **ASR 增量识别**：音频分片即传即识，无需等待用户说完。
    - **TTS 流式合成**：LLM 生成一小段话即触发 TTS 合成并下发音频分片。
- **智能打断 (Barge-in)**：前端实时检测用户人声，一旦发现用户开始说话，立即停止本地播放并通知后端重置状态。
- **本地部署优化**：利用本地网络的高带宽和低延迟，优先保证音频质量和响应速度。

## 3. 涉及改动点

### 3.1 后端改动 (Java/Spring Boot)
- **WebSocket 处理器扩展**：
    - 在 `com.lingshu.ai.web.websocket` 目录下新增或扩展 `VoiceChatHandler`。
    - 支持处理二进制消息（音频分片）和文本控制消息。
- **编排服务 (Orchestration Service)**：
    - 新增 `VoiceSessionManager` 维护每个用户的语音会话状态。
    - 集成流式 ASR 接口：实时将收到的音频字节流推送到 ASR 引擎。
    - 联动逻辑：ASR 识别到句尾 -> 触发 LLM 流式输出 -> LLM Token 累积到阈值 -> 触发流式 TTS -> 将音频分片写回 WebSocket。
- **打断逻辑实现**：
    - 接收到前端发来的 `STOP_AND_RESET` 指令时，立即取消当前的 LLM 生成线程和 TTS 合成任务。

### 3.2 前端改动 (Vue/TS)
- **新增 `useVoiceChat.ts` Composable**：
    - **音频采集**：使用 `AudioContext` 实时采样（采样率建议 16000Hz），并将音频数据转换为 `Int16Array` 或 `Opus`。
    - **流式发送**：每 50ms-100ms 通过 WebSocket 发送一个音频数据包。
    - **前端 VAD**：内置简单的能量检测逻辑，用于触发本地打断动画和控制指令。
- **音频播放器重构**：
    - 维护一个音频分片缓冲区（Audio Queue）。
    - 能够平滑地衔接后端推送过来的多个音频二进制片断。
- **UI 交互集成**：
    - 在 `ChatWindow.vue` 中增加语音通话模式入口。

## 4. 交互协议定义 (WS Message)

### 4.1 用户 -> 服务端
- `AUDIO_DATA (Binary)`：原始音频字节流。
- `{"type": "voice_start"}`：用户开始说话（手动触发或 VAD 触发）。
- `{"type": "voice_stop"}`：用户结束说话（发送后进入等待 AI 回复状态）。
- `{"type": "interrupt"}`：用户打断，要求 AI 立即停止。

### 4.2 服务端 -> 用户
- `AUDIO_SEGMENT (Binary)`：AI 合成的音频片段。
- `{"type": "asr_text", "text": "...", "isFinal": false}`：中间识别结果，用于在界面展示“正在听...”。
- `{"type": "ai_thinking"}`：告知前端 AI 正在生成回复，展示加载动画。
- `{"type": "ai_stop"}`：AI 播放结束信号。

## 5. 预期效果

- **交互延迟**：从用户说话结束到听到 AI 首个音节，本地环境下预期延迟 < 500ms。
- **交互感**：用户可以随时打断 AI，对话节奏更加接近真实人类通话。
- **系统性能**：通过流式处理减少内存积压，提高大并发下的响应稳定性。
