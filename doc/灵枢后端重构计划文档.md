# 灵枢 (LingShu) 后端重构计划文档 (Java -> Python)

## 1. 背景与目标
灵枢目前采用 Java (Spring Boot 3 + LangChain4j) 体系构建。为了更好地利用 Python 生态在 AI 领域的原生优势（如更快的模型集成、更丰富的算法库、更轻量级的开发体验），计划将后端重构为基于 Python 的现代化架构。

### 核心目标：
*   **架构现代化**：采用 FastAPI + AsyncIO 实现全异步流式处理。
*   **AI 生态集成**：利用 Python LangChain / LangGraph 的全量功能。
*   **性能对齐**：通过异步 IO 和轻量级框架，在保持 AI 逻辑复杂度的前提下提升响应速度。
*   **开发效率**：简化数据模型定义与业务逻辑开发。

---

## 2. 技术栈对比与选择

| 维度 | 当前 (Java) | 目标 (Python) | 理由 |
| :--- | :--- | :--- | :--- |
| **核心语言** | Java 21 | Python 3.12+ | 更好的 AI 支持与类型提示 |
| **Web 框架** | Spring Boot 3.2 (WebFlux) | **FastAPI** | 原生支持 Async，开发效率极高 |
| **AI 框架** | LangChain4j | **LangChain / LangGraph** | 功能最全，适合复杂 Agent 工作流 |
| **持久化 (Graph)** | Spring Data Neo4j | **Neomodel** | Python 下最成熟的 Neo4j OGM |
| **向量检索** | PgVector / EmbeddingStore | **LangChain VectorStore** | 统一的向量库抽象 |
| **数据校验** | Lombok + Bean Validation | **Pydantic v2** | 业界标准，性能卓越 |
| **任务调度** | Spring @Async / Scheduler | **APScheduler / Celery** | 灵活的后台任务管理 |
| **日志记录** | Logback / SLF4J | **Loguru** | 易于使用且功能强大 |

## 3. 业务逻辑拆解与架构设计

### 3.1 目录结构建议
```text
lingshu-python-backend/
├── app/
│   ├── api/                # 对应 lingshu-web (Controllers)
│   ├── core/               # 对应 lingshu-core (Service Logic)
│   │   ├── chat/           # 聊天引擎、流式处理
│   │   ├── memory/         # 记忆提取与检索算法 (核心逻辑)
│   │   ├── tasks/          # LangGraph 工作流定义
│   │   └── prompts/        # 动态提示词构建
│   ├── infrastructure/     # 对应 lingshu-infrastructure
│   ├── models/             # 对应实体与 DTO
│   └── utils/              # 工具类 (图像压缩等)
├── main.py                 # 应用入口
```

### 3.2 核心业务逻辑参考 (从 Java 提取)

#### A. 记忆模块 (Memory Service) —— “认知循环”逻辑
*   **事实提取流**：
    1.  **分析**：提取新事实并进行语义分类。
    2.  **冲突检测 (Contradicts)**：检测新事实是否与 Neo4j 中存量事实冲突。
    3.  **版本迭代 (Supersedes)**：检测新事实是否是存量事实的更新版本。
    4.  **持久化**：同步更新 Neo4j 关系图谱与 PgVector 向量索引。
*   **混合检索策略**：
    1.  **图谱优先**：基于实体提取进行 1-2 步路径检索，获取深度关联背景。
    2.  **增益评估**：计算图谱结果的信息量，若不足则触发 **向量补盲**。

#### B. 聊天模块 (Chat Service) —— “上下文装配”逻辑
*   **动态提示词构建**：合并 `Agent配置 + 用户关系 (Affinity) + 检索到的记忆上下文 + 实时情感分析`。
*   **多模态支持**：处理图片输入并确保其进入 LangChain 的消息链。
*   **异步后处理**：对话结束后，并行触发事实提取和亲密度更新，不阻塞 Token 输出。

#### C. 任务引擎 (Task Engine) —— 基于 LangGraph 的进化
*   **现状 (Java)**：通过手动序列化 `ChatMemory` 到 JSON 存档来实现任务的暂停与恢复，逻辑分散且维护困难。
*   **进化方向**：利用 **LangGraph** 重构任务执行逻辑。
    *   **节点化执行**：将“计划、执行、反思、修正”定义为图节点。
    *   **状态持久化**：利用 LangGraph 的 `Checkpointer` 原生支持任务断点恢复。
    *   **循环容错**：利用图的循环边处理工具调用失败后的自动修复逻辑。

## 4. 迁移路线图 (Phased Approach)

### 第一阶段：基础设施与数据模型 (1-2 周)
1.  使用 `Pydantic` 重写 DTO，使用 `Neomodel` 映射 Neo4j 节点，确保与旧数据兼容。
2.  配置 FastAPI 基础架构与异步日志系统。

### 第二阶段：核心业务逻辑移植 (2-3 周)
1.  **MemoryService 移植**：重点实现 Java 中的事实去重和冲突检测算法。
2.  **ChatService 移植**：基于 LangChain 实现流式对话与提示词装配逻辑。

### 第三阶段：任务引擎升级 (2 周)
1.  **LangGraph 集成**：将原本线性的任务执行逻辑改为基于图的工作流，实现更强的任务自主修正能力。

---

## 5. 潜在风险与应对
1.  **表结构兼容性**：Java 的 PgVector 存储格式与 Python 默认不同，需自定义适配器读取。
2.  **State 隔离**：Java 使用 `ThreadLocal` 处理请求上下文，Python 需切换为 `contextvars`。

---

## 6. 结论
重构不仅是语言切换，更是对“记忆认知”和“任务执行”两个核心引擎的升级。引入 LangGraph 将极大提升灵枢处理复杂长任务的稳定性。
